## Главный вывод

Основной предел качества сейчас задаёт не модель, а архитектура вокруг неё:

- сообщения разных чатов нельзя надёжно разделить;
- текущий turn дублируется, а reply-thread используется слабо;
- широкий контекст собирается по принципу «дать модели побольше», а не «дать только нужное»;
- personality перегружена правилами и динамическими фактами;
- route/fallback меняет доступный модели контекст;
- реальные production-сцены пока не превращены в повторяемые evals;
- часть естественных Telegram-сигналов — voice, links, stickers и reactions — либо не понимается, либо не подключена к общему AI pipeline.

Long-term memory — самый заметный частный случай этой общей проблемы.

Текущая long-term memory — это глобальный текстовый summary, который модель периодически переписывает из последних сообщений и предыдущей версии этого же summary. Затем весь summary и весь permanent lore целиком добавляются в system prompt. Такая схема:

- смешивает факты, временные события, интерпретации и шутки;
- позволяет ответам Jarvis становиться «фактами» о чате;
- сохраняет устаревшие пункты через рекурсивное переписывание;
- достаёт всю память независимо от темы;
- усиливает повторение одних и тех же callback'ов;
- не умеет объяснить, откуда взялось конкретное воспоминание.

Целевая схема:

```text
сообщения конкретного чата
        │
        ├── recent context: короткая история текущей сцены
        │
        └── memory extractor: только новые человеческие сообщения
                    │
                    ▼
             structured candidates
                    │
             deterministic policy
                    │
                    ▼
        memory_items с source, confidence и TTL
                    │
          selective retrieval по текущей теме
                    │
                    ▼
       3–5 релевантных записей в prompt, а не вся память
```

- [x] Production identity prompt хранится в таблице `prompt_versions`, а не в `.md`.
- [x] `PromptService.get_current_identity()` получает последнюю версию из БД и кэширует её.
- [x] На момент аудита активна версия prompt `v27`, созданная 10 сентября 2026 года; размер около 8.8K символов.
- [x] `.md`-файлы с identity являются историей/seed, но не production source of truth.
- [x] Основной persona route: OpenRouter; модель по умолчанию `x-ai/grok-4.6`.
- [x] Fallback и генератор summary: Together.ai; в окружении `Qwen/Qwen3.7-Max`.
- [x] Gemini используется отдельными fallback/мультимодальными маршрутами.
- [x] Смена основной модели сама по себе не исправит проблемы памяти, неверной атрибуции и загрязнённого контекста.

### Prompt stack основного ответа

Сейчас основной маршрут примерно собирает:

1. hard rules;
2. identity prompt из БД;
3. описание источника сообщения;
4. весь `chat-summary.md`;
5. весь `chat-lore.md`;
6. недавнюю историю сообщений;
7. дополнительный post-prompt непосредственно перед текущим сообщением;
8. текущее сообщение пользователя.

- [x] Stable personality, правила инструментов, социальные факты и динамическая память смешаны в одном большом контексте.
- [x] Одни и те же сведения об участниках дублируются между DB prompt и memory prompt.
- [x] В identity встречаются относительные по времени сведения, которые неизбежно устаревают.
- [x] Полный summary/lore получает высокий приоритет, потому что помещается внутрь system message.
- [x] Gemini получает rolling summary, но не permanent lore.
- [x] Simple/proactive route получает identity, но не получает summary/lore.
- [x] Поведение и «память» Jarvis поэтому зависят от того, через какой provider/route прошёл ответ.

### Хранение сообщений и recent context

- [x] В `messages` есть `id`, `user_id`, `message_text`, `timestamp`, `name`, `message_id`, `reply_to_message_id`.
- [x] В `messages` нет `chat_id`.
- [x] `_get_recent_group_messages(..., chat_id=...)` принимает `chat_id`, но SQL им не фильтруется.
- [x] Summary также строится без фильтра по чату.
- [x] При нескольких группах сообщения, recent context и память могут смешиваться.
- [x] Текущее сообщение сначала сохраняется в БД, затем попадает в загруженную history, после чего `_history_to_messages()` добавляет его в prompt ещё раз.
- [x] `reply_to_message_id` хранится, но практически не используется для точного retrieval контекста ветки.

### Telegram modalities и реакции

- [x] Photos уже анализируются через Gemini в mention/reply сценариях.
- [x] GIF/Telegram animation уже может скачиваться и анализироваться через Gemini при прямом mention или reply боту.
- [x] В обычном reply context чужой GIF без отдельного анализа представлен лишь маркером `[GIF]`.

- [x] Реакции сейчас проектировались как случайный дополнительный feature, а не как альтернатива текстовому ответу в low-value сценах.

### Experimentation и observability

### Текущая long-term memory

Файлы:

- `data/chat-summary.md` — rolling summary;
- `data/chat-lore.md` — permanent lore.

Пайплайн:

- [x] Раз в 24 часа фоновой задачей запрашиваются все сообщения за последние 48 часов.
- [x] В выборку входят и люди, и ответы Jarvis.
- [x] Модель одновременно получает сообщения, предыдущий summary и предыдущий lore.
- [x] Модель возвращает свободный Markdown вместо структурированных данных.
- [x] Валидация результата ограничивается минимальной длиной и обрезкой до 2500 символов.
- [x] Нет проверки, что обязательные секции существуют и содержат подтверждённые сведения.
- [x] Нет source message IDs, confidence, даты подтверждения, типа памяти, sensitivity или TTL.
- [x] Старый summary используется как вход для нового, поэтому исчезнувшие из 48-часового окна пункты продолжают жить.
- [x] Неограниченное число сообщений за 48 часов может создать слишком большой input в активном чате.

- [x] Файлы memory локальны, игнорируются Git и не синхронизированы между возможными инстансами.

### Permanent lore

- [x] Модель может сама вернуть секцию `НА ЗАКРЕП`.
- [x] `_promote_lore()` автоматически делает предложенные строки постоянными.
- [x] Human approval для auto-promote отсутствует, хотя ручной `/memory_pin` уже существует.
- [x] Dedup основан на substring и совпадении слов с заглавной буквы; он может как пропустить дубль, так и объединить разные факты об одном человеке.
- [x] При достижении cap в 20 строк нет политики замены, архивирования или понижения устаревшего lore.
- [x] Permanent lore используется не только persona chat, но и daily prophecy, поэтому плохая запись распространяется на несколько функций.
- [x] В коде daily prophecy уже зафиксирован реальный симптом: один lore callback выпал три раза из четырёх дней, после чего люди заметили «Эдик не отпускает».

### Команды управления памятью

- [x] `/memory` показывает rolling summary и permanent lore только администраторам.
- [x] `/memory_refresh` запускает фоновую пересборку, но не сообщает итоговый success/failure.
- [x] `/memory_clear` удаляет только summary, оставляя lore, хотя отвечает «Память обнулена».

- [x] После `/memory_clear` старые сообщения последних 48 часов могут снова восстановить удалённые пункты.
- [x] Нет точечного `/memory_forget`, `/memory_correct`, просмотра источников или отключения памяти для участника.

## Принципы целевой системы

- [ ] Summary использовать только как сжатие текущей сцены, а не как базу фактов.
- [x] Long-term memory хранить отдельными типизированными записями.
- [x] Каждая автоматически созданная запись обязана иметь provenance.
- [x] Ответ Jarvis никогда не является достаточным источником факта о людях или чате.
- [x] Third-party claim хранить как атрибутированное утверждение, а не объективный факт.
- [x] Не сохранять автоматически оскорбления, сексуальные характеристики, диагнозы и другие чувствительные оценки.
- [x] Episodic memory должна истекать; permanent memory должна быть редкой и управляемой.
- [x] Retrieval должен быть выборочным: отсутствие релевантной памяти лучше нерелевантного callback'а.
- [x] Personality отвечает за то, как Jarvis говорит; memory — только за то, что он обоснованно знает.
- [x] Сгенерированная память считается недоверенными данными, а не инструкцией.
- [x] Любую запись можно показать, исправить, забыть и проследить до источника. (`/mem_show`, `/mem_fix`, `/mem_forget`)

### 23.09.2026 — первые часы живого трафика: правки по данным
